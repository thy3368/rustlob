# 做市商视角：CEX 时延指标体系

> **核心认知**：做市商不关心"撮合引擎多快"，关心的是**每一个环节的时延确定性 + 尾部行为 + 极端行情退化**。  
> 时延不是单一数字，是一条链；链的强弱由最慢、最抖的那环决定。

---

## 一、总览：一笔订单的时延全链路

```
行情产生（撮合完成）
    ↓  [A] 行情分发时延]
    ↓  网络传输（去程）
    ↓  [B] 做市商策略决策]
    ↓  [C] 订单网关处理时延]
    ↓  [D] 网关→撮合内部传输时延]
    ↓  [E] 撮合匹配时延]
    ↓  [F] 成交后状态更新时延]
    ↓  [G] ACK / 推送返回时延]
    ↓  网络传输（回程）
    ↓  做市商接收
```

| 环节 | 主导方 | 是否 CEX 内生 | 说明 |
|------|--------|--------------|------|
| A. 行情分发 | CEX | ✅ 100% | 撮合完成 → 行情出网关 |
| B. 策略决策 | 做市商 | ❌ | 内部逻辑，通常 1~5µs |
| C. 订单网关处理 | CEX | ✅ 100% | 解码、鉴权、限流、风控预检 |
| D. 内部传输 | CEX | ✅ 100% | 网关 → 撮合引擎 |
| E. 撮合匹配 | CEX | ✅ 100% | 纯内存 LOB 操作 |
| F. 状态更新 | CEX | ✅ 100% | 资产账户、头寸、余额 |
| G. ACK/推送 | CEX | ✅ 100% | 结果序列化 + 推送 |
| 网络往返 | 物理 | ❌ | 做市商自己解决（co-lo） |

**结论**：一笔订单从"可以决策"到"知道结果"，端到端时延中 **CEX 内部环节占 70%~90%**（不含网络）。做市商能优化的只有网络距离和策略本身；其余全看 CEX 架构。

## 二、CEX 内生时延指标逐项拆解

### 1. 行情分发时延（Market Data Distribution Latency）

**定义**：撮合引擎产生成交/订单簿变更 → 行情推送网关出口的时延。

| 子指标 | 说明 | 典型值 |
|--------|------|--------|
| 行情生成到推送网关 | 序列化 + 路由 | 10~100µs |
| 增量行情分发 | 单笔成交/改单事件 | 50~200µs |
| 快照生成 | 全量订单簿快照 | 100µs~几ms |
| 行情合并窗口 | 合并多笔成交为一个事件 | 0~1ms（可配） |

**做市商关注点**：
- **是否合并行情**：合并 = 微观结构不可见，HFT 无法判断队列变化
- **序列号是否严格递增**：跳跃 = 丢事件，需要快照恢复，引入额外时延
- **极端行情下分发是否退化**：有的所行情推送在高频成交时排队

**尾部风险**：行情分发抖动 > 500µs → 做市商基于过期盘口决策 → 逆向选择亏损

---

### 2. 订单网关处理时延（Order Gateway Processing Latency）

**定义**：订单到达 CEX 公网网关 → 完成解码/鉴权/限流 → 进入撮合队列（或返回拒绝）的时延。

| 子指标 | 说明 | 典型值 |
|--------|------|--------|
| 协议解码 | FIX / JSON / 二进制 | 5~50µs |
| 鉴权/签名验证 | HMAC / Ed25519 / RSA | 10~200µs |
| 限流检查 | 令牌桶/滑动窗口 | 1~10µs |
| 风控预检 | 简单余额检查（同步）vs 无预检 | 0~几ms |
| 路由到撮合实例 | 按交易对路由 | 1~10µs |

**做市商关注点**：
- **风控预检是否同步**：如果是同步查余额，资产库压力大时网关时延直接飙到 ms 级
- **限流检查是否引入锁竞争**：高并发下令牌桶的 CAS 操作可能成为热点
- **是否支持 UDP/内核旁路**：FIX over TCP 的 syscall 开销 vs Raw UDP

**尾部风险**：网关处理从 50µs 跳到 5ms → 订单错过队列位置 → 吃不到价差

---

### 3. 网关→撮合内部传输时延（Internal Transport Latency）

**定义**：网关进程 → 撮合引擎进程的内部通信时延。

| 传输方式 | 典型值 | 确定性 |
|----------|--------|--------|
| 共享内存（SHM） | 1~5µs | 极高 |
| 本地 TCP loopback | 20~50µs | 高 |
| 跨机 TCP | 50~200µs | 中（受网络抖动） |
| RDMA | 5~10µs | 极高 |

**做市商关注点**：
- 是否同机部署（网关和撮合在同一台物理机）
- 是否共享内存（零拷贝）
- 队列深度是否有限制（满了怎么办）

**尾部风险**：跨机 TCP 在网卡中断 coalescing 时偶尔跳到 1ms+

---

### 4. 撮合匹配时延（Matching Latency）

**定义**：订单进入撮合主线程 → 完成 LOB 操作 → 生成成交事件 的耗时。

| 子指标 | 说明 | 典型值 |
|--------|------|--------|
| 新增订单（无匹配） | 插入 LOB | 1~5µs |
| 市价单（完全成交） | 遍历对手盘 | 2~10µs |
| 限价单（部分成交） | 匹配 + 插剩余 | 3~15µs |
| 撤单 | 从 LOB 移除 | 1~3µs |
| 批量操作 | 多笔订单 | 按比例增加 |

**做市商关注点**：
- **P50 没用，看 P99.9 / P99.99**
- 订单簿深度暴增时是否退化（O(log N) 的 log N 变大）
- 主线程是否被 WAL/行情/指标抢占
- 是否支持批处理（一个批次内多笔匹配）

**尾部风险**：正常 5µs，极端行情订单簿深度 10 万+ 时跳到 50µs → 取消单晚于成交单 → 库存风险

---

### 5. 取消确定性时延（Cancel Latency & Guarantee）

**定义**：Cancel 请求进入撮合 → 从 LOB 移除 → 返回 ACK 的时延，以及 Cancel 与 Match 的竞争关系。

| 子指标 | 说明 | 典型值 |
|--------|------|--------|
| Cancel-to-ACK | 纯处理 | 1~5µs |
| Cancel vs Match 竞争窗口 | 同一微秒内 Cancel 和 Match 谁赢 | 架构决定 |
| 批量 Cancel | 清盘口 | 5~50µs |

**做市商关注点**：
- **Cancel 是否保证在后续 Match 前生效**：如果 Cancel 和 Match 竞争同一把锁且 Cancel 输，就是实盘亏损
- 极端行情下 Cancel 是否会被限流
- 批量 Cancel 的原子性

**尾部风险**：这是 HFT 最怕的——Cancel 发了但单子被 Match 了，且无法提前预知

---

### 6. 成交后状态更新时延（Post-Trade State Update Latency）

**定义**：撮合引擎生成成交事件 → 资产账户服务更新余额/头寸/盈亏 → 结果可见 的时延。

| 子指标 | 说明 | 典型值 |
|--------|------|--------|
| 事件投递到资产服务 | 消息队列 | 50µs~几ms |
| 资产更新（内存事务） | 锁 + 更新 | 100µs~几ms |
| 持久化 | WAL/DB | 异步不等待 / 同步 1~10ms |
| 推送通知到客户端 | WS 推送 | 50~200µs |

**做市商关注点**：
- **是否异步**：大多数 CEX 是异步的，成交 ACK 回来但头寸还没更新
- 头寸可见时延：做市商需要知道"我到底赚了多少"才能继续挂单
- 跨分片账户更新延迟

**尾部风险**：成交了但余额没更新 → 后续下单被拒 → 策略中断

---

### 7. ACK / 推送返回时延（ACK / Push Return Latency）

**定义**：撮合完成 → 结果序列化 → 推送网关 → 出网的时延。

| 子指标 | 说明 | 典型值 |
|--------|------|--------|
| 结果序列化 | 生成 ACK/推送消息 | 5~20µs |
| 推送网关排队 | 高并发下 | 10~100µs |
| 出网 | 网卡 | 10~50µs |

**做市商关注点**：
- ACK 和推送是否走同一路径（REST vs WS）
- 推送是否保证顺序
- 推送丢失后的重传机制

## 三、合成时延指标（做市商内部使用，非 CEX 内生）

| 指标 | 构成 | 用途 |
|------|------|------|
| **Tick-to-Trade** | A + 网络去程 + B + C + D + E + G + 网络回程 | 端到端竞争力评估 |
| **Round-Trip Time (RTT)** | 发单 → ACK 的全链路 | SLA 基线 |
| **Time-to-Fill** | 发单 → 成交确认 | 策略盈利窗口 |
| **Time-to-Cancel** | 发 Cancel → Cancel ACK | 库存风险控制 |
| **Market Data Age** | 收到行情时，距撮合完成的真实时间 | 决策新鲜度 |

## 四、HFT vs General MM 的时延关注差异

| 维度 | HFT（高频） | General MM（普通） |
|------|-------------|-------------------|
| 关注环节 | A + C + E + Cancel + D | C + E + F + G |
| 时延量级 | µs 级 | ms 级 |
| 核心诉求 | 排队位置 + 取消确定性 | 稳定可预期 + 不超时 |
| 尾部关注 | P99.9 / P99.99 | P99 |
| 极端行情要求 | 不退化超过 10x | 不超时、不 503 |
| 网络优化 | 必须 co-lo | 可以跨城 |
| 最大恐惧 | Cancel 被 Match 吃掉 | 下单超时导致库存裸奔 |

| 指标 | SLA 建议 | 测量方式 |
|------|---------|---------|
| 撮合匹配 P99 | < 10µs | 交易所内部埋点 |
| 撮合匹配 P99.9 | < 50µs | 交易所内部埋点 |
| 行情分发 P99 | < 200µs | 交易所内部埋点 |
| 订单网关处理 P99 | < 500µs | 交易所内部埋点 |
| Cancel-to-ACK P99 | < 10µs | 交易所内部埋点 |
| 极端行情退化倍数 | < 10x 正常 P99 | 回放压测 |
| 热备切换 RTO | < 1s | 故障演练 |

## 六、一句话总结

> **做市商看 CEX 时延，不是看一个数字，而是看一条链：**
> - 行情分发是否及时、不合并、不乱序
> - 网关处理是否稳定、不随负载跳变
> - 撮合匹配是否快且确定、尾部不退化
> - 取消是否保证在匹配前生效
> - 成交后状态是否立刻可见
>
> **这些环节里，除了网络传输，全部由 CEX 架构内生决定。**
> 做市商能做的只有 co-location 和策略优化；剩下的，是交易所的骨头里长出来的东西，改不了。
