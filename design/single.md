
## Rust之从0-1低时延DEX：并发系统的一个深层物理规律：共享状态的高频变更最终都会收敛到单序列执行

---

## 一、先把这句话拆干净

> **"共享状态的高频变更，最终都会收敛到单序列执行。"**

三个关键词：

| 词 | 含义 |
|---|---|
| **共享状态** | 多个操作者都要读写的同一个东西（余额、book、key、行、文件） |
| **高频变更** | 冲突率足够高，并发控制机制开始"吃力" |
| **单序列执行** | 所有变更按一个确定的先后顺序，一条一条来 |

这句话的精髓在于：**不是"应该"单序列，是"不得不"单序列——因为其他路在高冲突下都会塌。**

---

## 二、为什么其他方案会塌

我们从最"自由"的并发模型开始，一层一层收紧，看每种方案在什么条件下失效。

### 1. 无锁并发（Lock-free / Wait-free）

**理想**：多线程同时改，靠 CAS / atomic 保证正确性。

**现实**：
- CAS 在**低冲突**下极快
- 冲突率一高 → 大量 CAS 失败 → 重试 → **重试放大流量**
- 重试本身又增加冲突 → 正反馈 → 活锁

数学上：

```
成功率 ≈ 1 - (N × P)   （N=线程数, P=单线程操作时间占比）
```

P 越大（操作越重）、N 越大（并发越高），成功率指数下降。

**结论**：无锁适合"短平快"的计数器，不适合"改余额+插流水+查风控"这种重操作。

### 2. 乐观并发控制（OCC / 版本号）

**理想**：先改，提交时检查版本，冲突了重试。

**现实**：
- 热点账户下，10 个并发请求，9 个版本检查失败
- 重试 9 次 → 每次又和新的请求冲突 → **重试风暴**
- 客户端看到的是：延迟飙高、成功率骤降

```
实际吞吐 ≈ 理论吞吐 / (1 + 重试倍数)
```

热点越热，重试倍数越大，吞吐反而下降。

**结论**：OCC 适合读多写少，不适合高频写共享状态。

### 3. 悲观锁（行锁 / mutex）

**理想**：谁先拿到锁谁改，其他人等着。

**现实**：
- 等待队列 → 上下文切换 → cache line 失效
- 锁持有时间越长，等待者越多 → **队列延迟累积**
- 死锁检测 / 超时 → 额外开销
- 锁粒度降到单行后，已经没有"更小"的锁了

```
延迟 = 锁等待时间 + 锁持有时间
锁等待时间 ∝ 并发请求数 × 锁持有时间
```

高频下，延迟无界增长。

**结论**：悲观锁是"把并行硬塞进串行"——但串行化发生在锁竞争里，不可控、不可预测。

### 4. MVCC（多版本并发控制）

**理想**：每个事务看到快照，提交时合并。

**现实**：
- 写仍然要序列化（WAL / undo log 的 append 是串行的）
- 快照版本管理有 GC 成本
- 长事务阻塞 GC → 版本链膨胀
- 高冲突下，快照间的合并成本指数上升

**结论**：MVCC 把"读"解放了，但"写"的序列化点还在——WAL 的 append 是单线程的。

---

### 5. 分布式锁 / 共识

**理想**：多机协调，谁拿到租约谁改。

**现实**：
- 网络 RTT 本身就是几毫秒
- 租约续期、故障切换、脑裂防护 → 额外复杂度
- 热点账户跨机房 → 网络延迟直接吃掉吞吐

**结论**：分布式锁把串行化的代价从"纳秒级"抬到"毫秒级"，吞吐反而更低。

---

## 三、为什么单序列执行是"吸引子"

上面五种方案，每种都在某个冲突率以下工作得很好。但**冲突率越过一个阈值后，它们的行为会收敛**：

| 方案 | 高冲突下的实际行为 |
|---|---|
| 无锁 CAS | 反复失败重试 → 等效串行 |
| 乐观版本 | 反复回滚重试 → 等效串行 |
| 悲观锁 | 排队等待 → 就是串行 |
| MVCC | WAL append 串行化 → 写路径串行 |
| 分布式锁 | 单 leader 处理 → 就是串行 |

> **所有并发控制机制，在高冲突下都会退化成"一个一个来"。**

区别只是：
- 退化发生在哪一层（应用？数据库？网络？）
- 退化是否可控（随机重试 vs 确定队列）
- 退化是否可预测（延迟有无界风险 vs 有界）

**单序列执行是主动选择这个退化点，把它从"意外退化"变成"设计意图"。**

---

## 四、单序列执行的本质优势

### 1. 正确性成本归零

```
单线程 / 单序列：
  - 无锁 ✅
  - 无死锁 ✅
  - 无重试 ✅
  - 无版本管理 ✅
  - 无 GC ✅
  - 无脑裂 ✅
  - 无一致性协议 ✅
```

所有并发 bug 的来源一次性消灭。

### 2. 延迟有界

```
单序列延迟 = 队列等待 + 单条处理时间
队列等待 = 排队长度 × 单条处理时间
```

只要单条处理时间可控，延迟就是**线性增长**，不会指数爆炸。

对比锁竞争：延迟可以无界（优先级反转、锁被长事务持有）。

### 3. 吞吐可预测

```
TPS = 1 / 单条处理时间 × 批量系数
```

一条简单公式，没有"冲突率""重试倍数""锁竞争概率"这些变量。

### 4. 可推演、可重放

给定输入序列，输出永远一样。这是：
- 数据库 WAL 重放
- 状态机复制（Raft / Paxos）
- 事件溯源
- 确定性模拟

的共同基础。

## 五、单序列 ≠ 单线程 ≠ 单核 ≠ 单机

这是最容易混淆的地方。工程上的单序列执行是**多维分片**的：

```
全局：多机、多核、多线程
  ↓ hash(key)
分片：每个分片独立
  ↓ 分片内
单序列：严格按序处理
```

| 系统 | 分片维度 | 单序列粒度 |
|---|---|---|
| Redis Cluster | slot (16384) | 单 slot 内单线程 |
| Kafka | partition | 单 partition 内有序 |
| Actor Model | actor | 单 actor 消息串行 |
| Aeron Cluster | Raft group | 单 group 内串行 |
| HyperCore | asset + account | 单市场/单账户串行 |
| MySQL InnoDB | 行 | 单行内行锁串行 |
| 数据库 WAL | 全局 | WAL append 全局串行 |

**每个系统都在"分片"和"串行"之间找平衡点**：
- 分片越细 → 并行度越高 → 但跨分片事务越难
- 串行粒度越粗 → 实现越简单 → 但热点越明显

---

## 六、那"分片"能不能无限细？

不能。因为分片本身有成本：

### 1. 跨分片操作

账户拆分后：
- 转账要从 A 子账户扣、B 子账户加
- 需要 2PC / Saga / 补偿事务
- 一致性模型降级（从线性一致变成最终一致）

### 2. 热点无法无限打散

有些热点天然是"一个"：
- 总账户余额（不能拆）
- 全局配置（不能拆）
- 序号生成器（不能拆）
- 全局限流器（不能拆）

这些只能单序列。

### 3. 分片数有管理成本

- 每个分片有状态、有快照、有恢复
- 分片迁移、再平衡
- 监控、运维复杂度线性增长

## 八、一句话总结

> **并发是常态，但共享状态的变更不是。高频下，所有并发控制都会退化成排队；聪明的系统主动选择排队，把"意外退化"变成"设计意图"，换来可预测、可推演、可扩展的架构。**

这不是某个人的偏好，是**状态、并发、一致性**这三个约束条件共同作用下，系统架构的唯一稳定解。
