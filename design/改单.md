这个问题问到点子上了。我从**交易所设计合理性**和**客户端工程合理性**两个角度来拆。

---

## 一、结论先行

> **原生 amend（Hyperliquid / OKX 合约 / Binance 合约）= 合理设计。**  
> **cancel + place = 妥协方案，不是合理设计。**

原因不是"方便不方便"，而是**语义正确性**。

---

## 二、为什么 cancel + place 不合理

### 问题 1：oid 变了，但业务逻辑上它是"同一笔意图"

你的策略想的是：

```
"把 BTC 买单从 50000 改到 51000"
```

cancel + place 之后：

```
旧单 oid=100，撤了
新单 oid=200，挂了
```

对策略来说这是**同一个操作**，但对系统来说变成了**两个对象**。后果：

- 仓位对账要处理"旧单消失 + 新单出现"
- 风控要区分"这是用户主动撤的还是改单导致的撤"
- WS 事件流里你会收到 Cancel + New + 可能中间的 Fill，顺序依赖复杂
- 回测重放时，cancel + place 的时序和实盘不一致

### 问题 2：中间态窗口

```
cancel 发出 → （网络延迟 / 撮合延迟） → place 还没到
```

这段时间里：
- 你的单子不在簿上
- 行情跳了，place 到的价格已经不利
- 或者更糟：cancel 成功但 place 被拒（余额不够 / 价格超出限制）

**cancel + place 不是原子的。** 中间态是不可控的。

### 问题 3：队列优先级丢失

做市商最在意这个。cancel + place = 重新排队。你的单子本来在 50000 的队首，改价后应该去 51000 的队尾——这是对的。但如果**只改 size**（比如减到一半），cancel + place 也会让你重新排队，白白丢了优先级。

---

## 三、为什么原生 amend 合理

### 1. 语义正确：改的是"属性"，不是"对象"

```
订单 = 一个对象
价格/数量 = 对象的属性
```

改属性 ≠ 换对象。就像你改一个 struct 的字段，不会 `drop` 再 `new`。

### 2. 原子性

amend 是**一次操作、一个结果**：
- 成功：属性更新，oid 不变
- 失败：原单不动

没有中间态。

### 3. 队列优先级可以精细化控制

| 改什么 | 队列行为 |
|--------|----------|
| 只改 size | 保留位置（合理，你还是你） |
| 改 price | 挪到新价位（合理，价格变了自然重排） |
| 改 size + price | 重排（合理） |

这是**撮合引擎内部可以做出的正确决策**，cancel + place 做不到。

### 4. oid 稳定 = 下游系统简单

```
风控：跟踪 oid=123 的敞口 → amend 后还是 oid=123 → 不用更新引用
对账：fill 事件里的 oid 永远指向同一笔业务意图
UI：用户看到的就是"改了价格"，不是"撤了一单又挂了一单"
```

---

## 四、那为什么还有交易所用 cancel + place

| 原因 | 说明 |
|------|------|
| 历史包袱 | 早期设计没考虑 amend，后来加成本高 |
| 架构解耦 | 网关和撮合引擎分离太彻底，amend 需要跨组件协调状态 |
| 现货比合约复杂 | 现货涉及两个资产、撮合簿更多，amend 的边界情况多 |
| 懒 | 真的 |

Binance 现货就是典型的"懒 + 历史包袱"：合约有 amend 接口，现货没有。不是技术上做不到，是优先级不够。

---

## 五、三种 amend 实现的合理性排名

| 排名 | 实现 | 理由 |
|------|------|------|
| 🥇 | Hyperliquid `modify` | 原生 amend，oid 不变，队列优先级规则清晰，batchModify 支持批量 |
| 🥈 | OKX `amend-order` | 原生 amend，ordId 不变，但 algo 和执行单分离增加了复杂度 |
| 🥉 | Binance 合约 `PUT /order` | 原生 amend，但部分场景会撤单（GTX 违规等），行为不完全可预测 |
| ❌ | cancel + place | 非原子、丢优先级、oid 变、中间态不可控 |

## 六、对你的 Rust 系统的启示

### 接口设计

```rust
trait OrderGateway {
    fn submit(&self, order: Order) -> Result<OrderAck, Error>;
    fn cancel(&self, id: &OrderId) -> Result<(), Error>;
    fn amend(&self, id: &OrderId, changes: AmendSpec) -> Result<AmendAck, Error>;
}
```

### 状态机

```rust
enum OrderEvent {
    Submitted { id, ... },
    Amended { id, old: AmendSpec, new: AmendSpec }, // id 不变
    Canceled { id, reason },
    Filled { id, ... },
}
// ❌ 永远不要有 Amend = Cancel + Submit 的语义
```

### 适配层

```rust
// 对不支持 amend 的交易所，适配层模拟（但标记为 fallback）
impl OrderGateway for BinanceSpotAdapter {
    fn amend(&self, id: &OrderId, changes: AmendSpec) -> Result<AmendAck, Error> {
        // fallback: cancel + place
        // 但返回时告诉你：这是模拟的，id 会变
        let new_id = self.cancel_and_place(id, changes)?;
        Ok(AmendAck::Simulated { old_id: id, new_id })
    }
}
```

## 七、一句话

> **合理的改单 = 原地改属性、oid 不变、原子操作。**  
> cancel + place 是"没有 amend 时的 workaround"，不是设计。  
> 做系统的时候：**接口层永远暴露 `amend`，底层不管交易所怎么实现，对上层屏蔽差异。**
