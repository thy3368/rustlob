## 大白话：三种测试的区别

**一句话：单元测试测"一个零件"，集成测试测"几个零件拼起来"，e2e 测试测"从用户按下按钮到拿到结果的整条完整链路"。**

范围从小到大：**单元 < 集成 < e2e**

---

### 用点外卖来类比

假设你是美团，要测"用户点外卖"这个功能：

| 测试类型 | 测啥 | 例子 |
|---|---|---|
| **单元测试** | 每个岗位单独考核 | 厨师炒菜好不好吃、骑手骑车快不快、打包员打包漏不漏汤、支付接口能不能扣款 |
| **集成测试** | 几个岗位串起来测 | 厨房出餐 → 骑手取餐 → 配送，这一段配合顺不顺（骑手到了餐还没好？取餐区找不到单？） |
| **e2e 测试** | 从用户视角测完整流程 | 用户打开 APP → 选餐厅 → 加购物车 → 支付 → 商家接单 → 出餐 → 骑手配送 → 用户收到外卖 → 评价，**整个流程从头到尾通不通** |

### 用技术场景来类比

假设你做了个"用户登录"功能：

```
用户输入账号密码 → 校验输入 → 查数据库 → 验证密码 → 生成 token → 返回登录成功
```

#### 单元测试：每个步骤单独测
```rust
#[test]
fn test_validate_input() { /* 测输入校验函数 */ }

#[test]
fn test_verify_password() { /* 测密码验证函数 */ }

#[test]
fn test_generate_token() { /* 测 token 生成函数 */ }
```
- 不连数据库、不发网络请求
- 每个测试只测一个函数
- 其他依赖全用 mock（假的）代替

#### 集成测试：几个步骤拼起来测
```rust
#[test]
fn test_auth_service() {
    // 真实连测试数据库
    let db = connect_test_db();
    // 测"校验 + 查库 + 验证密码"这一段配合
    let result = auth_service.login(&db, "user", "pass");
    assert!(result.is_ok());
}
```
- 真的连数据库、真的调多个模块
- 测模块之间接口对不对得上
- 但不经过网络、不模拟真实用户操作

#### e2e 测试：从用户视角测完整链路
```rust
#[test]
fn test_user_login_e2e() {
    // 启动整个服务（HTTP 服务 + 数据库 + 缓存）
    let server = start_full_server();
    
    // 模拟真实用户：发 HTTP 请求登录
    let response = http_client.post(server.url("/login"))
        .json(&{"username": "user", "password": "pass"})
        .send()
        .await;
    
    // 验证：状态码 200、返回了 token、数据库里登录状态更新了
    assert_eq!(response.status(), 200);
    assert!(response.json().await.unwrap()["token"].is_string());
}
```
- 整个系统真的跑起来（服务 + 数据库 + 缓存全启动）
- 模拟真实用户操作（发 HTTP 请求、点按钮）
- 验证从输入到最终输出的完整结果

### 关键区别速查表

| 维度 | 单元测试 | 集成测试 | e2e 测试 |
|---|---|---|---|
| **测试范围** | 一个函数/一个模块 | 多个模块协作 | 整个系统完整链路 |
| **外部依赖** | 全 mock（假的） | 部分真实（如数据库） | 全部真实（服务+DB+网络） |
| **跑的速度** | 极快（毫秒级） | 中等（秒级） | 慢（分钟级） |
| **发现啥问题** | 逻辑写错、算法错 | 模块接口对不上、配合有问题 | 整个流程走不通、用户体验有问题 |
| **写的人** | 开发 | 开发/测试 | 测试/开发 |
| **跑的频率** | 每次保存都跑 | CI 里跑 | 发布前跑/夜间跑 |
| **稳定性** | 极稳定 | 较稳定 | 容易 flaky（时好时坏） |
| **Rust 代码位置** | `src/` 里 `#[cfg(test)]` | `tests/` 目录 | `tests/` 目录或单独 e2e crate |

---

### 各自能发现什么独有的问题？

#### 单元测试能发现，其他发现不了：
- 算法写错了（比如排序逻辑反了）
- 边界条件没处理（空字符串、负数、超大数）
- 函数返回值算错了

#### 集成测试能发现，单元测试发现不了：
- A 模块传的数据格式，B 模块解析不了
- 数据库字段长度不够，存不下加密后的密码
- 事务回滚没做好，一半成功一半失败

#### e2e 测试能发现，前两个都发现不了：
- 用户点了登录按钮，页面转了半天圈然后超时（网络/服务整体性能问题）
- 登录成功了，但跳转页面白屏（前后端配合问题）
- 支付成功了，但订单状态没更新（跨服务链路问题）
- 整个流程能走通，但用户要等 30 秒（体验问题）

### 为什么需要三种？不能只写 e2e 吗？

不能，因为：

1. **e2e 太慢**：跑一次要几分钟，开发不可能每次改代码都等几分钟
2. **e2e 太脆弱**：网络抖一下、数据库慢一点，测试就失败了（不是代码问题，是环境问题）
3. **e2e 定位问题难**：e2e 失败了，你只知道"登录失败了"，但不知道是密码加密错了还是数据库挂了
4. **单元测试快且准**：改了代码立刻跑，1 秒出结果，失败了直接告诉你哪个函数错了

**正确的姿势**：单元测试大量写（金字塔底层），集成测试适量写，e2e 只写最核心的几条链路（比如登录、下单、支付）。

### Rust 里的对应实现

```
my-project/
├── src/
│   ├── lib.rs
│   ├── auth.rs          ← 单元测试写这里（#[cfg(test)]）
│   └── db.rs
└── tests/
    ├── auth_integration.rs   ← 集成测试（多模块协作）
    └── e2e_login.rs          ← e2e 测试（启动整个服务，发 HTTP 请求）
```

```bash
cargo test --lib          # 只跑单元测试
cargo test --test auth_integration  # 跑某个集成测试
cargo test --test e2e_login         # 跑 e2e 测试
```

### 一句话总结

> **单元测试是"体检时每个器官单独查"——心电图、B超、验血各查各的；集成测试是"几个器官一起查"——查心肺联动、肠胃配合；e2e 测试是"让你跑个 800 米"——看整个身体从发令枪响到冲过终点线能不能完整跑下来。前者保证零件不坏，中者保证协作顺畅，后者保证整车能上路。**
