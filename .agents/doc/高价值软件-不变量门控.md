# AI coding之不变量门控

## 本文定位

- 作为《高价值软件-门控框架》的专题补充，聚焦“不变量”这一类高价值软件的核心约束。
- 不重复门控系统总论，只展开不变量如何被识别、表达、承载、验证和反哺。
- 语境以 RustLOB / 金融交易系统为主，兼顾 AI Coding 带来的不变量破坏风险。

## 为什么不变量是高价值软件的核心门控对象

### 高价值软件的失败形态

- 不是所有 bug 都同等重要。
- 高价值软件最危险的问题，通常不是页面展示错误，而是核心业务事实被破坏。
- 金融系统中，一次错误可能导致资产错配、账务不平、重复成交、风险穿透、审计不可追溯。

### 不变量与普通校验的区别

- 普通校验关注一次输入是否合法。
- 不变量关注系统在任意合法状态迁移后，必须始终成立的业务事实。
- 普通校验可以出现在边界输入处；核心不变量必须进入领域模型、用例、测试和线上校验闭环。

### 门控目标

- 在需求和设计阶段显式列出不变量。
- 在代码结构中把不变量放到正确层次。
- 用计算型门控优先验证确定规则。
- 用概率型门控辅助发现遗漏、漂移和语义冲突。
- 用线上缺陷和异常数据反哺不变量清单。

## 业务不变量的定义及相关方法论

### 定义

业务不变量是指：在一个业务边界内，不论输入顺序、系统负载、实现细节、存储方式和技术框架如何变化，都必须持续成立的业务约束。

### 不变量的常见形态

- 数量守恒：资产、余额、仓位、成交数量不能凭空增加或消失。
- 状态合法：订单、转账、清算、结算只能沿合法状态机迁移。
- 因果正确：后继事实必须由明确的前置事实推出。
- 唯一性：订单号、成交号、幂等键、账务流水号不能重复冲突。
- 单调性：版本号、事件序号、账本序号、撮合序号只能按规则递增。
- 对称性：买卖双方成交、扣款入账、手续费收取必须成对或成链闭合。
- 可追溯性：关键状态变化必须能回放到原始命令、授权主体和事件链。

### 识别方法

- 从钱、货、权、风险、时间序列五类对象出发识别。
- 从状态机出发识别：哪些状态不能跳过，哪些状态不能回退，哪些终态不可逆。
- 从账务分录出发识别：是否借贷平衡，是否有来源单据，是否可重放。
- 从撮合链路出发识别：订单、成交、余额、持仓、行情之间是否因果闭合。
- 从事故复盘出发识别：历史缺陷破坏了哪个必须永远成立的事实。
- 从并发和重试出发识别：重复提交、乱序事件、部分失败是否仍保持业务事实正确。

### 不变量表达方式

- 需求文档：用业务语言列出必须保持的事实。
- 设计文档：标明不变量归属的实体、聚合、use case、账务链路或事件链路。
- 代码：用类型、构造函数、实体方法、状态机、use case 校验和 Changes 表达。
- 测试：用实体测试、use case 测试、集成测试、E2E 测试和属性测试表达。
- 线上：用审计任务、对账任务、指标告警和异常样本沉淀表达。

## 金融领域常见业务不变量

### 账户与余额不变量

- 账户余额不能为非法负数，除非业务明确允许信用或透支。
- 可用余额、冻结余额、总余额之间必须满足定义关系。
- 冻结、解冻、扣减、入账必须有来源单据和幂等键。
- 同一笔资金变化不能被重复应用。
- 资产精度、舍入规则和最小变动单位必须一致。

### 订单生命周期不变量

- 订单只能沿合法状态机迁移。
- 已终结订单不能再次成交、取消或修改。
- 已成交数量不能超过原始委托数量。
- 剩余数量、已成交数量、取消数量之间必须闭合。
- 修改订单不能绕过价格、数量、账户、风控约束。

### 撮合与成交不变量

- 一笔成交必须同时关联买单和卖单。
- 成交价格、数量必须符合撮合规则和盘口优先级。
- 买卖双方成交数量必须一致。
- 撮合后订单剩余数量、成交记录、余额或持仓变化必须一致。
- 同一撮合事件不能重复生成成交。

### 持仓、保证金、风险不变量

- 持仓数量、开仓、平仓、成交和资金费用之间必须可解释。
- 保证金占用、可用保证金、风险率必须按同一规则计算。
- 杠杆、强平、减仓等动作不能绕过风险边界。
- 风控检查与最终状态变化之间不能使用不一致的状态快照。
- 仓位方向、净持仓、逐仓或全仓模式必须语义一致。

### 清结算与账务不变量

- 每一笔账务流水必须有业务来源。
- 借贷、收付、扣减、入账必须平衡。
- 清算结果必须能由成交、费用、资金费率、活动规则等前置事实推出。
- 结算单据不能重复执行。
- 账务更正必须保留反向或补充流水，而不是静默覆盖事实。

### 行情与事件序列不变量

- 行情快照和增量事件必须有明确序号或版本关系。
- 增量事件不能跨越无法解释的缺口。
- 最新价、成交量、盘口变更必须来自成交或订单簿变化。
- 同一事件流中，事件时间、撮合序号、发布序号的语义不能混用。
- 回放事件应能重建关键状态或定位不可重建的外部依赖。

### 审计、权限、幂等与可追溯不变量

- 关键命令必须能追溯到发起主体、授权上下文和请求来源。
- 幂等键相同的命令不能产生多组互相冲突的业务事实。
- 权限检查不能只存在于 inbound adapter。
- 审计日志不能替代业务事件，但必须能关联业务事件。
- 失败、拒绝、回滚、补偿路径也应保留可解释记录。

## 不变量在 core / adapter / infra 中的承载位置

### core.entity

- 承载可复用业务规则和实体自身不变量。
- 适合表达值对象合法性、实体构造约束、单实体状态迁移、同一聚合内部一致性。
- 典型例子：余额不能非法扣减、订单终态不可再变更、账务流水必须有来源单据。

### core.use_case

- 承载跨实体、跨聚合、跨单据链的业务动作不变量。
- 以 `Command + GivenState -> Changes` 表达一次业务目标。
- 适合表达撮合后订单、成交、余额、持仓、账务之间的因果闭合。
- `Changes` 是 use case 的业务真相，应能投影为可持久化、可回放、可发布的事实。

### adapter

- `adapter.inbound` 负责把 HTTP、WebSocket、CLI、MQ 等输入转换为 use case 的 command/query。
- `adapter.outbound` 负责实现 use case 定义的 port，并适配 DB、外部 API、消息、展示输出。
- adapter 可以做格式校验、协议转换、鉴权上下文装配，但不承载核心业务不变量。
- 如果某条规则离开 HTTP 或 DB 后仍必须成立，它就不应只写在 adapter。

### infra

- 负责 DB、消息、运行时、监控、锁、事务、唯一索引、定时任务等机制性保障。
- 适合保障唯一性、持久化原子性、消息投递、审计存储、指标采集、告警触发。
- infra 可以强化不变量执行效果，但不能成为业务不变量的唯一表达位置。

## 业务不变量分别适合放在哪些类型的门控中

### 文档型门控

- 需求中是否显式列出关键不变量。
- 设计中是否说明不变量所属实体、use case、账务链路或事件链。
- 需求、设计、代码之间的不变量描述是否漂移。
- 是否明确正常路径、拒绝路径、补偿路径、重放路径的不变量。

### 架构门控

- 核心不变量是否放在 `core.entity` 或 `core.use_case`。
- adapter 是否只做协议转换和输入输出适配。
- infra 是否只提供机制保障，而不是隐藏业务规则。
- use case 是否保持 `Command + GivenState -> Changes` 的可审查形态。
- 跨聚合协作是否留在 use case，而不是下沉到某个聚合成员。

### 单元测试门控

- 值对象精度、舍入、边界值测试。
- 实体构造和实体方法的不变量测试。
- 状态机合法迁移和非法迁移测试。
- 纯业务规则的快速、确定性测试。

### use case 测试门控

- 覆盖 `Command + GivenState -> Changes` 的 happy path。
- 覆盖非法命令、状态错配、余额不足、订单终态、重复执行等拒绝路径。
- 验证 `Changes` 中的订单、成交、余额、持仓、账务、事件因果一致。
- 验证 replayable events 能表达后续持久化、发布和回放所需事实。

### 集成/E2E 门控

- 验证跨模块、跨聚合、跨系统链路的不变量。
- 覆盖撮合、清算、账务、行情、推送、审计之间的端到端一致性。
- 覆盖重试、乱序、超时、部分失败、重复消息等真实运行场景。
- 验证 adapter 和 infra 没有改变 core 已经保证的业务语义。

### 性能门控

- 不变量检查不能破坏关键路径延迟。
- 区分快路径同步检查、异步审计检查、离线对账检查。
- 对撮合、下单、撤单、行情推送等路径设置基线。
- 关注额外分配、锁竞争、序列化开销和状态装载成本。

### 概率型门控

- LLM 辅助发现需求、设计、代码、测试中的不变量遗漏。
- LLM 辅助检查同一不变量在多处描述是否语义冲突。
- LLM 辅助识别 AI Coding 常见破坏模式。
- 概率型结果先作为风险提示和人工评审输入，不宜直接作为早期硬拦截。

## AI Coding 场景下的不变量破坏模式

### 规则放错层

- 把余额、订单状态、风险规则写在 controller、handler、DB mapper 中。
- 用 adapter 输入校验替代 core 业务不变量。
- 把 infra 的唯一索引误当成业务语义本身。

### 只补 happy path

- 只让主流程通过，缺少拒绝路径、重复执行、乱序、并发和补偿路径。
- 只验证返回值，不验证状态变化和事件链。

### 语义弱化

- 为了编译通过引入弱语义字段、空分支、默认值或吞错。
- 把明确业务错误降级为通用错误。
- 把不可逆状态改成可随意覆盖。

### 因果链断裂

- 生成了余额变化却没有来源单据。
- 生成了成交却没有同步更新订单剩余数量。
- 生成了事件却无法回放到同一业务事实。

### 精度与边界遗漏

- 混用浮点数和定点数。
- 忽略最小价格单位、最小数量单位、手续费精度和舍入方向。
- 没有覆盖零值、极值、边界数量和跨精度转换。

## 不变量门控的落地优先级

### 第一阶段：关键不变量清单

- 先覆盖资金、订单、成交、持仓、账务、审计。
- 每个核心 use case 至少列出必须保持的不变量。
- 每条不变量标注所属层次：`core.entity`、`core.use_case`、`adapter`、`infra`。

### 第二阶段：计算型硬门控

- 编译、Lint、架构规则、单元测试、use case 测试优先。
- 对确定规则建立低误报、可重复执行、可硬拦截的检查。
- 优先拦截新增 `unwrap()` / `expect()`、空分支吞错、adapter 承载业务规则等基础问题。

### 第三阶段：业务链路门控

- 为撮合、清算、账务、行情、推送建立集成和 E2E 不变量测试。
- 补齐拒绝路径、重复请求、乱序事件、部分失败和重放验证。
- 建立关键链路性能基线。

### 第四阶段：概率型辅助门控

- 用 LLM 做需求/设计/代码/测试漂移分析。
- 用 LLM 做不变量遗漏扫描和 AI Coding 风险审查。
- 将高置信、低争议问题逐步沉淀为计算型规则。

### 第五阶段：线上反哺

- 从事故、告警、对账差异、审计异常中补充不变量。
- 将线上异常样本转化为回归测试。
- 将反复出现的问题升级为文档、架构、测试或性能门控。

## 总结与检查清单

### 四个核心问题

- 不变量是什么：系统在任意合法状态迁移后仍必须成立的业务事实。
- 有哪些不变量：资金、订单、成交、持仓、账务、行情、审计、权限、幂等、追溯。
- 放在哪里：实体自身规则放 `core.entity`，跨实体/跨聚合业务动作放 `core.use_case`，adapter 做适配，infra 做机制保障。
- 怎么门控：文档先显式化，架构防放错层，测试做确定验证，性能守住关键路径，概率型辅助发现遗漏，线上持续反哺。

### 最小检查清单

- 需求是否列出关键不变量。
- 设计是否标明每条不变量的承载位置。
- `core.entity` 是否承载实体自身不变量。
- `core.use_case` 是否以 `Command + GivenState -> Changes` 承载业务动作不变量。
- adapter 是否没有隐藏核心业务规则。
- infra 是否只做机制性保障。
- 单元测试是否覆盖实体和值对象不变量。
- use case 测试是否验证 `Changes` 的因果一致。
- 集成/E2E 测试是否覆盖跨模块不变量。
- 性能门控是否覆盖关键路径。
- LLM Review 是否用于发现遗漏、漂移和语义冲突。
- 线上异常是否反哺到不变量清单和回归测试。
